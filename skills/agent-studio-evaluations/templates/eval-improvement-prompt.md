# Copy-paste prompt: evaluate an agent and propose improvements

Shareable prompt for ANY AI coding agent (no skills or prior context needed).
Paste the block below into the agent's chat. It installs the algobot CLI,
guides authentication, runs an Agent Studio evaluation with generated cases,
analyzes the results, and proposes improvements without touching the
production agent.

Requires `algobot-ai` 2.1.0 or later, which ships the `evals` command
group; the prompt itself verifies this in Step 1 and stops with a clear
message if the installed version is older. The flow below uses
Agent Studio-generated cases; building eval cases from the agent's real
conversation history is a separate flow documented in the
agent-studio-evaluations skill.

---

# Agent Studio: evaluate my agent and propose improvements (algobot CLI)

You are helping an Algolia customer evaluate their Agent Studio agent with the
`algobot` CLI and propose concrete improvements based on the results. Work step
by step, explain what you are doing, and keep the user in the loop. You may
INSTALL software and RUN evaluations freely, but you must NEVER modify or
publish the user's agent without their explicit approval.

## Step 1: Install the CLI

1. Check Node.js >= 18 (`node --version`). If missing, tell the user to install
   it from https://nodejs.org and stop.
2. `npm install -g algobot-ai@latest` (evaluations require 2.1.0+).
3. Verify the version and that evaluations are available:
   `algobot --version` (must be >= 2.1.0) and `algobot evals metrics list`.
   If `evals` is unknown, STOP and tell the user to upgrade:
   `npm i -g algobot-ai@latest`.

## Step 2: Authenticate

You need two values from the user:
- Their **Application ID** (Algolia dashboard, top-left or Settings > Applications)
- An **Admin API Key** (Settings > API Keys > Admin API Key)

Never echo the key back, never paste it into a command (it would land in
the agent transcript and shell history), and never write it into a file
that could be shared or committed. Offer the user two options:
- Interactive: `algobot init` (wizard, creates a profile)
- Scripted: the USER sets `ALGOLIA_APP_ID` and `ALGOLIA_API_KEY` in their
  own shell session; you then run the algobot commands in that environment
  without ever handling the literal key

Verify auth: `algobot agents list`. If it returns `[]` while the user knows
they have agents, warn about the known limitation: the CLI targets the EU prod
host (`agent-studio.eu.algolia.com`); agents hosted in other regions are not
reachable. Confirm with `algobot --verbose agents list` before assuming a
credential problem.

## Step 3: Pick the agent and the metrics

1. `algobot agents list --jq '.[] | {id, name, status}'` and ask the user which
   agent to evaluate. Record its `id`, `status`, and index name
   (`algobot agents get <id>` -> `tools[].indices[]`).
2. `algobot evals metrics list` and present the catalog. If it returns an
   empty list, the metric catalog is not provisioned for this application:
   STOP and tell the user to contact Algolia support. Recommended first
   pass: `faithfulness` + `tone`. Ask the user to confirm the metric set.
3. Note: the agent does NOT need to be published to be evaluated.

## Step 4: Run the evaluation (Agent Studio-generated cases)

1. Announce the cost first and get the user's go-ahead BEFORE creating the
   experiment. With generated cases, the run costs `num-cases x number of
   selected metrics` completions of the agent (each on the user's LLM
   provider) plus one judge call per case. Suggest `--num-cases 50` for a
   first pass (results below ~50 cases per metric are flagged
   `underpowered`); do not scale up without asking.
2. On approval, launch (cases are GENERATED by Agent Studio, grounded on the
   index and the agent profile - no dataset authoring needed):
   `algobot evals experiments create --index-name <idx> --agent-uuid <agentId> --metric-ids <m1,m2> --num-cases 50`
3. Record the experiment id, the dataset id, and later the run id: the
   comparison step needs the SAME dataset to be meaningful.
4. This is asynchronous and can take minutes to hours. Poll every ~30 s at
   first: `algobot evals experiments get <expId>`. Do not block forever:
   after ~15 minutes of `running`, tell the user the evaluation continues
   server-side and they can ask you to check again later with the same
   command. Statuses: resolving_profiles -> generating -> awaiting_review ->
   running -> judging -> completed.
4. If it stalls in `awaiting_review`, the generated cases need a review pass:
   - `algobot evals datasets list-cases <datasetId> --status suggested`
   - `algobot evals datasets bulk-status <datasetId> --status approved --filter-status suggested`
   - `algobot evals datasets finalize <datasetId>`
   - `algobot evals experiments run <expId>`
5. Find the run id with `algobot evals experiments runs <expId>`.

## Step 5: Analyze the results

1. `algobot evals runs summary <expId> <runId>`: per-metric passRate, meanScore,
   confidence intervals, `underpowered` flag. Check `underpowered` and the CI
   before drawing any conclusion.
2. `algobot evals runs judgments <expId> <runId> --limit 200`: one verdict per
   case with the judge's `reason`. Cluster the reasons into failure themes with
   counts (e.g. "empty retrieval context: 6", "style violations: 3").
3. For 2-3 representative failures, drill down:
   `algobot evals runs case <expId> <runId> <caseId>` where `<caseId>` is the
   judgment's `evalCaseId` field (NOT the judgment `id`, which returns a
   misleading 404). Read the retrieved records and tool calls to confirm the
   root cause.

## Step 6: Propose improvements (do NOT apply them)

Map each failure theme to its knob:
- Tone violations -> agent instructions: add an explicit OUTPUT STYLE contract
  (e.g. "never use exclamation marks, emojis, or hype").
- Faithfulness failures (claims not supported by retrieved records) -> agent
  instructions: add an ACCURACY section ("only reference attributes that appear
  in tool output"); also check the search tool's `returnedFields`.
- Irrelevant/wrong results -> index-side: ranking, searchable attributes,
  query rules (Algolia CLI/dashboard territory).
- Tool errors or wrong tool use -> agent tool configuration.

Present to the user: the failure themes with counts, ONE concrete proposed
change at a time (exact instruction text to add or setting to change), and the
expected impact. Do not apply anything yourself.

If the user asks you to apply the changes, first pick the mode:
- Agent is `published` and was created by the user: default to the clone
  path below (a draft clone serves no traffic, so zero risk); direct edits
  to a published agent need explicit confirmation.
- Agent is a `[eval-tuning ...]` copy this loop created earlier: edit it
  directly, no new clone needed.

Then follow the safe clone path:
1. Snapshot the current config: `algobot agents scaffold <agentId>` (keep the
   output for rollback).
2. `algobot agents create --config agent-config.json --name "<name> [eval-tuning <date>]"`.
   The clone stays in `draft` - drafts are evaluable and serve no traffic.
   Recent CLI releases (2.1.0+) strip deprecated config fields and capture
   `providerId` in the scaffold, so the clone is usually ready as-is; if the
   scaffold still contains deprecated fields such as `enableAlgoliaMcp`,
   remove them and link the provider with
   `algobot agents patch <cloneId> --json patch.json` where
   `patch.json` is `{"providerId": "<uuid>"}`.
3. Patch the clone: `algobot agents patch <cloneId> --json patch.json`.
4. Re-run the eval on the clone with `--dataset-id <baselineDatasetId>` and
   compare: `algobot evals compare --run-a <baselineRun> --run-b <cloneRun>`.
5. Promotion applies the winning changes to the ORIGINAL agent, not the
   clone: the clone has a different agent id and the frontend keeps
   embedding the original one, so switching traffic to the clone is not a
   promotion path. Show the user the exact config diff first, warn that
   publishing makes the change immediately live for all users, then patch
   and publish the original agent only on explicit approval.

## Rules

- Never launch bare `algobot` with no arguments (it opens an interactive TUI
  that hangs scripts). Always use explicit subcommands.
- All commands print JSON; `--jq` is built in. Note that `--jq` returns
  JSON-quoted strings: strip quotes with `tr -d '"'` before reusing an id.
- Never print, store, or transmit the API key.
- If a command fails with HTTP 422 mentioning a provider or scaffold issue,
  the agent likely has no LLM provider linked: tell the user to check
  Settings > Providers in the Agent Studio dashboard.
